# 지식 그래프 정확도 개선 설계

- 날짜: 2026-11-10
- 상태: 사용자 검토 대기

## 목표

지식 그래프(온톨로지)의 품질을 올려 두 가지를 좋게 만든다.

- **A. 성도 연결선**: 엉뚱한 연결은 줄고, 있어야 할 연결은 생긴다.
- **B. AI 채팅 검색**: 질문에 맞는 노트를 찾는다.

관계 자체의 사실 정확성(별자리 관계도, 근거 문장 강화)과 추출 모델 교체는 범위 밖이다. 모델은 평가에서 비교만 한다.

## 현재 상태 (2026-11-10, 운영 DB 읽기 전용 집계)

활성 노트 586개, 추출 모델 `gemini-3.1-flash-lite`. 추출 정확도는 측정된 적이 없다 (`graph_eval` 정답 세트는 가상 샘플 1건).

| 항목 | 값 |
|---|---|
| 추출 성공 | 580/586 (실패 6건은 모두 Gemini 503) |
| 근거 문장이 확인된 관계 | 2,178/4,709 (46%) |
| 객체 관계 중 `관련있다` | 1,234/4,143 (30%) |
| 한 노트에만 있는 개념 | 2,127/2,727 (78%) — 3단어 이상 이름은 94%, 다른 개념명을 포함하는 이름 955개 중 754개 |
| 공백·기호 차이로 갈라진 개념 | 0 (표기 흔들림은 원인이 아님) |
| `인스턴스이다` 규칙 위반 | 91/654 (14%), `하위클래스이다` 위반 8건 |
| 40,000자 초과로 잘리는 노트 | 25개 |
| 연결 근거가 있는 노트 쌍 | 85,374쌍 (전체 쌍의 50%), 그중 `relation` 74,465 |
| 허브 개념 | 0 (최다 등장 개념이 노트 112개, 허브 기준은 176개 초과) |
| 실제 그려지는 선 | 2,408개, 99%가 `relation`, 노트당 최대 103개 |
| 선이 없는 노트 | 38개 |

원인:

1. 관계 근거가 개념 단위로 퍼진다 — 관계 하나가 주어 개념을 가진 모든 노트 × 목적어 개념을 가진 모든 노트를 잇는다 (`routers/search.py` `_PairEvidence`).
2. 관계 점수에 희소성(IDF)과 노트 내 중요도(`weight`)가 없다.
3. 허브 기준(노트의 30%)이 노트 586개에서는 걸리는 개념이 없다.
4. 개념 이름이 활동 명사구("X 설치 방법")로 파편화되어 노트 사이에서 합쳐지지 않는다. 질문과도 일치하지 않아 B에도 영향을 준다.
5. 공유 개념의 `kind`를 마지막 분석이 덮어써서(`graph_extraction._resolve_concept`) 먼저 저장된 관계가 규칙을 어긴다.
6. 40,000자 뒤는 추출되지 않는다.

## 진행 순서와 채택 규칙

① 평가 기준 → ② 연결 계산 → ③ 추출 개선 → ④ 긴 노트 분할. 단계마다 기준선 대비로 평가한다.

**채택 규칙**: 그 단계의 목표 지표가 오르고, 다른 층의 지표가 3%p 넘게 떨어지지 않으면 채택한다. 구체적인 목표치는 ①의 기준선을 본 뒤 사용자와 정한다.

## ① 평가 기준

앱 동작은 바꾸지 않는다. 모두 `backend/graph_eval`에 둔다.

| 층 | 대상 | 데이터 | 지표 | AI 호출 |
|---|---|---|---|---|
| 연결 (A) | `/discoveries/routes`가 그리는 선 | 표본 노트 30개의 상위 5개 선(약 150쌍)에 관련/무관 판정 | 연결 정밀도@5, 선 없는 노트 수 | 없음 |
| 검색 (B) | `routers/ai._retrieve_notes` (상위 `RAG_LIMIT`=5) | 질문 20~30개 + 정답 노트 ID | 적중률@5, MRR | 없음 |
| 추출 | `graph_extraction.parse_graph(call_model(...))` | 가상 노트 10~15개 정답 세트 (기존 `cases/` 형식) | 관계 정밀도·재현율, 개념 재현율, 3회 실행 평균과 범위 | 있음 (가상 데이터만) |
| DB 진단 | 운영 DB 읽기 전용 | — | 위 "현재 상태" 표의 항목 | 없음 |

- 운영 DB에는 쓰지 않는다. 보고서는 기존처럼 `graph_eval/reports/`(git 제외)에 JSON과 Markdown으로 남긴다.
- **정답 세트 작성 (사용자 결정: 방식 B)**: Claude가 실제 노트를 읽고 연결 판정과 질문·정답 초안을 만들고, 사용자가 검토한다. 실제 노트에서 나온 정답 세트와 판정 CSV는 git에서 제외한 `graph_eval/local/`에 둔다. 가상 노트 추출 정답 세트는 `cases/`에 커밋한다.
- 표본은 고정 시드로 뽑는다. 판정용 CSV는 Excel에서 열 수 있게 `utf-8-sig`로 쓴다.
- 판정 풀(pooling): 알고리즘이나 파라미터를 바꿔 처음 보는 쌍이 상위 5개에 들어오면 그 쌍만 추가로 판정한다. 보고서는 미판정 쌍 수를 함께 표시하고, 미판정이 남아 있으면 그 결과로 채택 여부를 정하지 않는다 (먼저 판정을 채운다).
- 조정용/확인용 분리: 판정 노트 30개 중 20개로 ②의 파라미터를 고르고, 나머지 10개로 과적합을 확인한다.

## ② 연결 계산 수정

AI 호출 없음. `routers/search.py`의 `_PairEvidence`와 그 테스트만 바꾼다. 응답 형식은 그대로라 프론트엔드 변경은 없다.

| 문제 | 변경 |
|---|---|
| 관계 근거가 개념 단위로 퍼짐 | 관계 (s, p, o)는 그 관계가 **노트 a 또는 b에서 추출된 경우에만** a–b의 근거다. a가 관계를 말하고 b가 반대편 개념을 가진 경우만 잇는다 |
| 관계 점수에 희소성 없음 | 관계 점수 = 관계 강도 × 상대 노트 쪽 개념의 IDF |
| 언급만 된 개념도 동등 | 공유 개념과 관계 점수에 `min(두 노트의 weight) / 3`을 곱한다 |
| 허브 필터 미작동 | 허브 비율 `_HUB_SHARE`를 평가로 정한다 (후보 0.05 / 0.1 / 0.2) |
| 약한 쌍도 5개를 채움 | 최소 점수 `_MIN_ROUTE_SCORE` 미만 쌍은 그리지 않는다 (값은 평가로 정함) |

- 유지: 태그·키워드 근거와 그 규칙, 확정·거부 항로, 노트당 5개 상한, 선 종류(`kind`) 정의.
- 영향: 성도 연결선과 "미개척 항로" 패널(`/discoveries`)이 같은 계산을 쓴다. 허브 기준을 공유하는 `/routes/path`도 바뀐다. AI 채팅 검색(`graph_retrieval`)은 영향 없음.
- 파라미터는 파일 상단 상수로 두고, 조합은 6개 이하만 시험한다.
- 테스트(먼저 실패하게 작성): 다른 노트에서 나온 관계로는 연결되지 않는다 / 드문 개념의 연결 점수가 흔한 개념보다 높다 / 최소 점수 미만 쌍은 빠진다.
- 성공 기준: 연결 정밀도@5 상승, 선 없는 노트 수가 크게 늘지 않음(허용 폭은 기준선 확인 후 합의).

## ③ 추출 개선

전체 재분석이 필요하다. `services/graph_extraction.py`, `db.py`, `graph_eval`을 바꾼다.

### 1. `kind` 다수결

- `note_concepts`에 `kind` 컬럼을 추가해 노트별 판단을 저장한다. 기존 행은 현재 `concepts.kind`로 채운다. **DB 스키마 변경이므로 마이그레이션 전에 DB를 백업한다.**
- 개념의 `kind`는 그 개념을 쓰는 노트들의 다수결로 정한다. 동률이면 기존 값을 유지한다. 노트 재분석·삭제 시 다시 계산한다.
- 저장된 `kind`와 맞지 않는 구조 관계(`인스턴스이다`, `하위클래스이다`)는 연결 계산(`search.py`)과 검색 확장(`graph_retrieval.expand`)에서 건너뛴다.

### 2. 개념 이름 규칙 (프롬프트)

- 이름은 대상을 가리키는 가장 짧은 표준 이름으로 쓴다.
- 활동 명사구("Docker 설치", "RAG 구축 방법")는 개념으로 만들지 않는다. 대상(Docker)만 노드로 두고 내용은 관계로 표현한다.
- 3단어 이상 이름은 고유명사일 때만 쓴다.

### 3. 기존 개념 목록 제공

- 노트 본문에 이름이나 동의어가 나오는 기존 개념을 최대 50개까지 프롬프트에 "이미 쓰는 이름"으로 넣고, 같은 대상이면 그 이름을 쓰게 한다. 일치 판정은 `graph_retrieval.match_seeds`와 같은 규칙(영문은 단어 경계, 그 외는 2자 이상 부분 일치)을 쓴다.
- 후보는 **2개 이상 노트에서 쓰이고 3단어 미만인 개념**으로 한정한다. 재분석 중에는 아직 옛 그래프의 파편화된 이름이 남아 있으므로, 그 이름이 다시 퍼지지 않게 하기 위함이다.
- 전체 어휘(약 2,700개)는 넣지 않는다 — 토큰 비용과 무관한 이름에 끌리는 문제 때문.
- 평가 재현: 정답 세트에 선택 항목 `known_concepts`(이미 쓰는 이름 목록)를 추가해 같은 조건으로 채점한다.

### 4. 모델

`gemini-3.1-flash-lite`를 유지한다. 평가에서 상위 모델(flash)과 비교만 하고, 차이가 비용을 감당할 만큼 크면 별도로 제안한다.

### 재분석 절차

1. 가상 노트 추출 평가에서 기준선 대비 개선을 확인한다.
2. 운영 DB를 백업한다.
3. 사용자 확인을 받는다 (노트 본문이 다시 Gemini로 전송되고, 분당 10건으로 약 1시간 걸린다).
4. `POST /graph/rebuild`로 재분석한다 (이 경로가 `graph_hash`를 지워 강제 재추출함을 확인함).

### 테스트와 성공 기준

- 테스트(먼저 실패하게 작성): 다수결로 `kind` 결정 / 기존 개념 후보 선택과 제외 규칙 / 이름 규칙이 프롬프트에 들어감.
- 추출 평가: 개념 재현율, 관계 정밀도·재현율이 기준선 이상 (3회 평균).
- DB 진단: `kind` 규칙 위반 0건, 고립 개념 비율과 3단어 이상 이름 비율 감소.
- 최종: 연결 정밀도@5와 검색 적중률@5 상승.

## ④ 긴 노트 분할

`services/graph_extraction.py`, `services/graph_worker.py`를 바꾼다. 대상은 40,000자 초과 노트(현재 25개).

- **분할**: 40,000자 이하 노트는 지금과 같이 한 번 호출한다. 초과하면 마크다운 제목(`#`) 경계를 우선, 없으면 빈 줄, 그래도 없으면 글자 수로 자른다. 코드 블록 중간은 자르지 않는다. ③-3의 기존 개념 후보는 조각마다 그 조각 기준으로 고른다.
- **병합**: 개념은 `norm`이 같거나 동의어로 겹치면 합친다(`weight`는 큰 값, 동의어는 합집합). 상한은 개념 15 × 조각 수(최대 30), 관계 25 × 조각 수(최대 50). 넘으면 `weight` 높은 순으로 남긴다. 근거 문장은 노트 전체 본문과 대조한다.
- **실패**: 조각 하나라도 실패하면 노트 전체를 `failed`로 두고 기존 그래프를 유지한다. 일부만 반영된 그래프는 만들지 않는다.
- **속도 제한**: 분당 10건을 노트 단위가 아니라 모델 호출 단위로 센다.
- 테스트: 경계 선택(제목 우선, 코드 블록 보존) / 병합 / 조각 실패 시 기존 그래프 유지 / 호출 단위 속도 제한.
- 평가: 약 45,000자 가상 노트 1건을 정답 세트에 추가하고, 40,000자 뒤에만 나오는 개념의 재현율을 본다. DB 진단에서 25개 노트의 40,000자 뒤 개념이 그래프에 들어가는지 확인한다.

## 보안·데이터 취급

- 커밋하는 정답 세트와 예시는 가상 데이터만 쓴다. 실제 노트 기반 판정·질문은 `graph_eval/local/`(git 제외)에만 둔다.
- 연결 정답 초안 작성 시 표본 노트 내용이 Claude(Anthropic)로 전송된다 — 사용자 동의함.
- 전체 재분석 시 노트 본문이 Gemini로 다시 전송된다 — 실행 전 별도 확인.
